01

Краткая оценка проекта

Проект реалистичный, но это не «приложение на выходные». По объёму он делится на три очень разные части, и важно не путать их сложность.

Ядро трекера

Шаблоны, активная тренировка, подходы, история, PR, графики. Технически несложно, но требует аккуратности: здесь живут ваши данные, которые нельзя терять.

Каталог упражнений

Самая недооценённая часть. Код каталога пишется за пару дней, а вот данные и картинки с чистой лицензией — это недели работы и главный риск проекта.

AI-тренер

Технически это не «прикрутить чат». Это отдельный слой инструментов поверх вашей базы плюс минимальный сервер. Зато он не влияет на работоспособность трекера.

03

Почему выбран именно этот стек

Expo + Expo Go — потому что у вас Windows

Это ключевое ограничение всего проекта. Чистый React Native CLI потребовал бы Xcode и, значит, Mac. Expo Go — готовое приложение из App Store, которое загружает ваш JavaScript по QR-коду. Компьютер отдаёт код, iPhone его выполняет. Xcode не нужен вообще до этапа 20.

expo-router вместо React Navigation напрямую

Файл app/(tabs)/index.tsx = экран. Не нужно вручную описывать навигаторы и передавать параметры через типы — путь и есть API. Для новичка это на порядок меньше кода, который можно сломать. Внутри это всё равно React Navigation, так что потолка возможностей мы не касаемся.

SQLite, а не AsyncStorage / файлы / облако

Приоритет №1 из вашего списка — «надёжность сохранения тренировок». SQLite даёт транзакции (подход либо записан целиком, либо не записан), индексы (история за годы не начнёт тормозить), агрегаты прямо в запросе (объём за неделю считает база, а не JS) и FTS5 для поиска по каталогу. AsyncStorage — это key-value помойка, на ней вся статистика из раздела 21 писалась бы вручную и медленно.

Чистый SQL + repositories, а не ORM

Правило из раздела 43 — «никаких SQL-запросов внутри экранов» — выполняется не наличием ORM, а наличием слоя repositories. Каждый файл вида WorkoutRepository.ts — это единственное место, где живёт SQL для своей таблицы. Экран вызывает workoutRepo.getLastPerformance(exerciseId) и ничего не знает про таблицы. Плюс: когда что-то работает медленно, вы видите ровно тот запрос, который выполняется.

Zustand, а не Context, для активной тренировки

Здесь важна причина, а не мода. Активная тренировка — это объект, который меняется при каждом нажатии на «+2.5 кг». Если положить его в React Context, перерисовываться будет всё поддерево, включая таблицы всех остальных упражнений. Zustand позволяет компоненту подписаться ровно на один подход (useWorkoutStore(s => s.sets[setId])), и остальной экран не перерисовывается. Это прямо влияет на приоритет №2 — скорость UX в зале. Context мы всё же используем, но только для того, что меняется редко: тема, соединение с БД, настройки.

gifted-charts, а не Skia

Графики нужны на этапе 9, а Expo Go мы хотим сохранить как можно дольше. gifted-charts рисует через react-native-svg, который входит в Expo Go. Для 50–200 точек на графике прогресса разницы в производительности вы не заметите.

Принцип отбора

Библиотека попадает в проект, только если: (1) она совместима с Expo Go, либо мы осознанно принимаем переход на dev build ради неё; (2) она заменяет минимум 200 строк нашего кода; (3) она живая. Всё остальное пишем сами — компонентов в приложении меньше, чем кажется.

Ключевое архитектурное решение

Инструменты выполняются на телефоне, а не на сервере. Модель говорит «мне нужен getExerciseHistory("bench-press", "90d")» → прокси возвращает этот запрос приложению → приложение выполняет SQL локально → отправляет обратно только результат этого запроса. Сервер остаётся тупым ретранслятором и никогда не видит вашу базу. Это даёт и приватность (раздел 56), и простоту: сервер — это один файл на ~100 строк.

Правило, которое нельзя нарушать

Число, которое видит пользователь, всегда приходит из analytics/, а не из языковой модели. Модель получает {"volumeKg": 8940, "prevVolumeKg": 8420, "changePct": 6.2} и её работа — превратить это в человеческий текст. Она физически не должна ничего умножать: в системном промпте это запрещено, а в контекст всегда кладутся готовые значения (раздел 17).

Структура базы данных SQLite

Одна база gymlog.db, внутри — три логические зоны. Разделение важно, потому что у них разный жизненный цикл.

Каталог

Заполняется из поставляемого JSON. При обновлении приложения может быть перезалит целиком. Пользователь его не меняет (кроме своих упражнений).

Данные пользователя

Тренировки, подходы, PR, вес тела, настройки. Не трогается никогда, кроме миграций. Это то, что мы обязаны не потерять.

Служебное

Кеш медиа, кеш статистики, AI-переписка. Полностью восстановимо — можно удалить и пересобрать.

Глобальные соглашения

Система миграций

Никакого «удалите приложение и поставьте заново». Версия схемы живёт в PRAGMA user_version, миграции — пронумерованный массив функций, применяются по порядку в транзакции.

src/db/migrations/index.ts — принцип
export const migrations: Migration[] = [
  { version: 1, up: async (db) => { /* CREATE TABLE … */ } },
  { version: 2, up: async (db) => { /* CREATE VIRTUAL TABLE exercise_fts … */ } },
  { version: 3, up: async (db) => { /* ALTER TABLE workout_set ADD COLUMN rpe REAL */ } },
];

export async function migrate(db: SQLiteDatabase) {
  const { user_version: current } = await db.getFirstAsync<{ user_version: number }>(
    'PRAGMA user_version'
  );
  for (const m of migrations.filter(m => m.version > current)) {
    await db.withExclusiveTransactionAsync(async (tx) => {
      await m.up(tx);
      await tx.execAsync(`PRAGMA user_version = ${m.version}`);
    });
  }
}
Правило миграций

Файл миграции, который хоть раз уехал на телефон, больше никогда не редактируется. Ошибку исправляет только новая миграция с новым номером. Иначе у вас и у будущего вас будут разные базы при одинаковом user_version.

Про вес тела в формулах

Для bodyweight_* берётся вес тела на дату тренировки из body_weight_entry (ближайшая запись не позже даты), и он записывается в снимок подхода. Иначе, взвесившись через год, вы «задним числом» перепишете весь свой прошлый объём — классический баг таких приложений.

Активная тренировка не живёт в памяти. Каждое изменение подхода немедленно пишется в SQLite (сессия в статусе active), zustand-стор — лишь зеркало для быстрой отрисовки. Это прямое требование приоритета №1 — надёжность сохранения.

Как работает импорт

Семейства и разделение статистики

family_id — это только семантическая связь. Жим лёжа, наклонный жим и жим в Смите имеют family_id = 'bench_press', но их история никогда не смешивается: любая статистика группируется строго по exercise_id. Семейство используется ровно в двух местах: подбор замены (раздел 36 ТЗ) и подсказка AI «это родственные движения» — и AI получает их как отдельные наборы чисел, а не как один.

Пользовательские упражнения — полноправные

Своё упражнение — это обычная строка в exercise с is_custom = 1, source = 'user'. Никаких отдельных таблиц. Поэтому оно автоматически работает в поиске, шаблонах, истории, статистике, PR, графиках и AI — без единой строчки дополнительного кода. Это ключевая причина, почему каталог и «свои упражнения» — одна таблица.

Поиск по тысячам упражнений

Используем SQLite FTS5 — он включён в expo-sqlite по умолчанию (опция плагина enableFTS = true). Индекс строится как external content таблица над exercise, а синонимы, мышцы, оборудование и теги склеиваются в отдельные колонки индекса.

миграция 002 — поисковый индекс
CREATE VIRTUAL TABLE exercise_fts USING fts5(
  name_ru, name_en, aliases, muscles, equipment, tags,
  content='',                        -- сами храним, чтобы класть склеенные поля
  tokenize = "unicode61 remove_diacritics 2",
  prefix = '2 3 4'                   -- поиск начинает работать со 2-й буквы
);

Как ищем

// SearchService.search("гантели грудь")
1. Нормализация запроса
   trim → lower → ё→е → убрать лишние пробелы → выкинуть стоп-слова
2. Построение FTS-запроса: каждое слово с префиксом
   «гантел*  AND  груд*»
3. Ранжирование: bm25 с весами колонок —
   имя важнее синонима, синоним важнее тега
   ORDER BY bm25(exercise_fts, 10.0, 8.0, 5.0, 3.0, 3.0, 2.0), popularity DESC
4. Пусто? → мягкий fallback: LIKE '%…%' по name_ru/name_en/alias
5. LIMIT 40 + keyset-пагинация при скролле

«гантели грудь»два токена: equipment + muscles, AND-логика
«lat pulldown»name_en

Производительность в UI

  • Debounce ввода 180 мс + отмена предыдущего запроса.
  • Запрос возвращает только id, name_ru, name_en, equipment, primary_muscle, thumb — не всю карточку упражнения.
  • Фильтры (раздел 8 ТЗ) применяются как WHERE-условия к тому же запросу, а не в JavaScript.
  • Пустой поиск = не «все 3000», а секции: «Недавние», «Избранные», «Из ваших шаблонов», «Популярные».
Запасной план

FTS5 в Expo Go включён по умолчанию, но проверим фактически на этапе 4 одним запросом при старте. Если по какой-то причине он недоступен, SearchService прозрачно переключается на LIKE-поиск по денормализованной колонке search_blob — интерфейс об этом не узнает. Именно поэтому поиск спрятан за сервисом, а не написан прямо в экране.

Слой ContextBudget

  • Жёсткий лимит ~8 000 символов на контекст. Не влезает — режем по приоритету: сначала упражнения без изменений, потом старые сравнения, потом заметки.

1. Все числа приходят из приложения. НИКОГДА не вычисляй, не оценивай

2. Структурируй ответ: Данные → Интерпретация → Рекомендация.
3. Не смешивай разные упражнения. Жим в Смите — не жим штанги.
4. Ты не врач. Боль, травма, головокружение, потеря сознания →
   не ставь диагноз, порекомендуй обратиться к специалисту и не давай нагрузку.
5. RIR/RPE меняют смысл: 8 повторов с RIR 3 и с RIR 0 — не одно и то же.
6. Коротко. Русский язык. Без мотивационного шума и без восклицаний через строку.
7. Не утверждай причинно-следственную связь там, где есть только корреляция.

  • Каждый результат ограничен по размеру (обрезаем и помечаем "truncated": true).
  • Инструменты только читают. Ни один не может изменить вашу базу. Планы тренировок AI пока не пишет.
  • Ответ инструмента всегда содержит единицы измерения и период — чтобы модель не «догадывалась».
  • В UI показываем, какие инструменты сработали: видно, что ответ основан на данных, а не на фантазии.
