# IPBan Dashboard

Дашборд для просмотра логов IPBan, RadiusProxy (двухфакторка) и журнала Windows
в одном месте. Это один файл `index.html` — никакого сервера и установки не требуется,
всё обрабатывается локально в браузере, файлы никуда не отправляются.

## Что показывает

- **Обзор** — сводная статистика: баны, неудачные входы, сессии, суммарное время работы.
- **Логи** — все источники в одной ленте, с переводом сообщений на русский,
  фильтрами по типу/уровню/дате и скрытием служебных строк.
- **IP-адреса** — сводка по каждому адресу: баны из БД IPBan, неудачные входы,
  первое/последнее появление.
- **Пользователи** — сводка по каждому человеку сразу из всех источников
  (2ФА + Windows + IPBan). По клику разворачивается полная хронология событий
  и список сессий.
- **Сессии** — когда человек подключился, когда отключился, сколько работал.
- **Таблицы БД** — просмотр `ipban.sqlite` как есть.

## Как пользоваться

1. Откройте `index.html` в браузере (Chrome или Edge — нужен доступ к папкам).
2. Нажмите **«➕ Добавить папку с логами»** и выберите папку.
3. Повторите для каждой папки — они объединяются в общую картину. Обычно это:
   - `C:\IPBan` — логи и база IPBan
   - `C:\RDP-Configuration-FontvielleRDP\RadiusProxy\logs` — логи двухфакторки
   - папка с выгрузкой журнала Windows (см. ниже)

Файлы логов определяются по содержимому, а не по имени, так что любая схема
ротации (`logfile_900`, `log-2026-07-08-1`, …) подхватывается автоматически.
Браузер запоминает выбранные папки, поэтому при следующем открытии они
подключаются сами (иногда потребуется один клик «Восстановить доступ» —
без подтверждения пользователя браузер не даёт странице читать диск).

## Журнал Windows

Браузер не может читать бинарный журнал Windows (`.evtx`) напрямую — такого API
не существует ни в одном браузере. Поэтому события выгружаются в CSV скриптом
`export-windows-events.ps1`, а дашборд читает эту папку как обычный источник.

Запустите PowerShell **от имени администратора** (журнал Security иначе недоступен):

```powershell
# Разовая выгрузка за последние 7 дней
.\export-windows-events.ps1 -OutputDir C:\IPBan\windows-events

# Автоматическая выгрузка каждые 15 минут через Планировщик задач
.\export-windows-events.ps1 -OutputDir C:\IPBan\windows-events -Install

# Убрать задачу из Планировщика
.\export-windows-events.ps1 -Uninstall
```

Затем добавьте папку `C:\IPBan\windows-events` в дашборде — дальше она будет
обновляться сама, а кнопка «Обновить сейчас» и автообновление подхватят новые данные.

### Какие события собираются

| ID | Журнал | Событие |
|----|--------|---------|
| 4624 | Security | Вход в систему |
| 4625 | Security | Неудачный вход (содержит IP — связывается с банами IPBan) |
| 4634 / 4647 | Security | Выход из системы |
| 4778 / 4779 | Security | Переподключение / отключение сессии |
| 21 / 23 / 24 / 25 | TerminalServices | Вход, выход, отключение и переподключение RDP-сессии |

Дашборд также понимает сырую выгрузку `Get-WinEvent | Export-Csv` — нужные поля
он в этом случае достаёт из текста сообщения.

### Сотрудники за своими компьютерами

Человек, который работает за своим ПК, входит в систему **на своей машине** —
событие 4624 пишется в журнал этого компьютера, а не сервера. Поэтому выгрузка
с одного сервера покажет только тех, кто заходил на него самого (например, на
RDS-шлюз). Чтобы видеть всех, собирайте события с рабочих станций:

```powershell
# Перечислить машины вручную
.\export-windows-events.ps1 -OutputDir C:\IPBan\windows-events -ComputerName PC-01, PC-02

# Или взять все компьютеры домена (нужен модуль ActiveDirectory)
$pcs = (Get-ADComputer -Filter { OperatingSystem -like "*Windows*" }).Name
.\export-windows-events.ps1 -OutputDir C:\IPBan\windows-events -ComputerName $pcs
```

Для удалённого чтения журналов нужны права администратора домена и доступ к
удалённым машинам (служба «Удалённый вызов процедур» и разрешающее правило
брандмауэра «Удалённое управление журналом событий»).

### Что считается сессией

Сессией считается только интерактивный вход — локальный (тип 2), по RDP
(тип 10), разблокировка экрана (тип 7) и кэшированный вход (тип 11).

Сетевые входы (тип 3) сессиями **не** считаются: это обращения к общим папкам,
групповые политики и служебная аутентификация. На домене их десятки тысяч, у
них не бывает выхода, и раньше они заполняли вкладку «Сессии» бесконечными
строками «ещё активна». В логах они по-прежнему видны.

Адреса `fe80::…` и `169.254.…` тоже отфильтрованы — это link-local, то есть
сетевая карта в пределах своего сегмента, а не адрес, откуда кто-то подключался.

### Как считается длительность сессии

Вход (4624) связывается с выходом (4634/4647) по **Logon ID**, а не по времени.
Это принципиально: если у человека открыто несколько сессий одновременно
(обычное дело для RDP), сопоставление «по порядку» дало бы неверную длительность.
Если выход не найден, сессия помечается как «ещё активна» — время не додумывается.

Учётные записи самой системы (`SYSTEM`, `DWM-1`, `UMFD-0`, `КОМПЬЮТЕР$` и т.п.)
отфильтровываются, иначе они забивают статистику по людям.
